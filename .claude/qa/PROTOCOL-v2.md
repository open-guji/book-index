花費 471 美元。本文據那一輪的實測，重排剩下的 2,807 條該怎麼並行。

## 二、真正的病根：**沒有地方寫「這條看過了，沒問題」**

全庫 17,288 條記錄有 `ai_note`（自由文字），**零條有結構化的裁決欄位**。
頂層欄位掃過一遍：`merged_in` 213、`merged_into` 82、`merged_from` 36、
`merge_history` 31——**連併條都有四種寫法**，卻沒有一個 `verdict`。

後果是複合的：

- `scan.py` **無法把裁過的排除**，所以數字不會降。今天殘餘 2,807 裡，
  以「ai_note 含判語字樣」粗估，**只有約 12% 帶得上判過的痕跡**。
- 於是每一道新開，都要把同一批記錄重讀一遍——**上下文就是這樣燒光的**。
- 各道報的「判常態 619」是計數，不落在記錄上；**下一輪沒人看得到**。

**唯一做對的是 entity/CBDB 道**：它把 573 條切分錯誤的裁決寫成 `verdicts.tsv`，
可覆核、可覆用。v2 把這件事變成全庫的地基。

## 三、v2 的三個結構改動

### 改動一：裁決落賬（最要緊，先做，其餘都靠它）

新增 `.claude/qa/verdicts.jsonl`，一行一裁，append-only：

```json
{"id":"d59f2xxx","check":"C","verdict":"normal","rule":"C-注疏","round":24,
 "by":"lane-C","at":"2026-09-07T..","why":"role=注，後代注家繫前代之書，庫例判常態"}
```

- `scan.py` 加 `--exclude-adjudicated`：凡 (id, check) 已有 `normal` 之裁者不再報。
- `verdict` 只三種：`normal`（是常態，不必動）／`fixed`（已改）／`open`（待人裁，附
  known-issues 檔名）。
- **判準（`rule`）是第一等公民**：同一個 rule 可以一次落幾百條，且日後可整批翻案
  ——翻案只要按 `rule` 撈回來重判，不必重掃全庫。

**立刻可回收的**：以下 **510 條**是各道早已判定的常態，只因無處可寫而每輪重計——

| 判準 | 條數 |
|---|---:|
| I `juan_differ` 卷數異即異書 | 256 |
| C `annot` 後代注疏角色繫前代之書 | 181 |
| Y `variant` 佛典異譯 | 67 |
| Y `same_name` 同名異書 | 6 |

一條 rule 落賬，2,807 立刻變 2,297，而且**不是把問題掃到地毯下——每條都留著 why 與 rule**。

### 改動二：按**判準**分道，不按**期**分道

實測 2,728 條相異記錄中，**92%（2,518）只被一個檢命中**；命中兩個以上的只 210 條，
且集中在少數幾對（C-L 106、I-Y 33，其餘皆 ≤10）。
**所以按檢分道幾乎不撞車**，把重疊的檢配在同一道即可歸零。

一道只讀一條判準，不必裝 19 類；併條在道內完成，不必找協調者。

### 改動三：工具凍結，並與資料分離

v1 有兩次共用工具的 bug 讓全庫同時停擺（`TITLE_RE` 覆寫、`description` 型別崩潰）。
v2：**`scan.py` 只有協調者可改**，且改後必須跑 `--period`（不是只跑全庫——坑 54）
並比對前後數字才可推。車道要新檢，提規格給協調者，不自行改。

## 五、兩段式，不是一段式

**第一段（五道並行，各自約一小時）：立判準、批量落賬。**
每道自己那一類**跨全部期**抽 30 條（坑 45：抽自己沒想到的那一片），
寫成一條 rule，把 rule 能決的全部落 `verdicts.jsonl`。
產出：judgment rule ＋ 大幅縮小的「待逐條讀」清單。

**第二段（依第一段餘量重新配道）：逐條裁。**
只讀 rule 決不了的。到這一步才需要讀著錄原文、上網查證。

分兩段的理由：v1 是一開始就逐條讀，於是把上下文花在「確認這條沒問題」上——
而那正是可以規則化的部分。

## 六、協調者只做三件事

v1 的協調者既管工具、又管裁決、又代辦積壓，成了瓶頸。v2 縮成三件：

1. **守賬**：`verdicts.jsonl` 的格式與去重、`scan.py` 的排除邏輯、閘（`verify.py`）。
2. **守工具**：`scan.py` 唯一可改者；車道提規格，協調者改並回歸測試。
3. **一條待裁佇列**：車道遇到要人定的，寫下就繼續往下做，**不停下來等**。
   協調者定期把這個佇列整理給使用者。

   **2026-09-07 使用者定，待審之物一律放
   `overview/项目进展/古籍索引网站/待审元数据/`，所有會話皆同。**
   `.claude/qa/for-user.md` 已改為一枚指路牌，不再受理。
   放法：**一個會話一個檔**，`<會話名>-<YYYYMMDD>-<短題>.md`；規矩見該資料夾之 `README.md`。
   協調者維護 `00-待裁总清单.md`（匯總）與 `01-全库质量复查-待裁清单.md`（`report.py` 生成）。
   **放檔之外仍要落賬**（`verdict=open`）——只放檔不落賬，下一道會把同一批再讀一遍。

**協調者不再代辦積壓。** 車道停擺就補一道新的接手，不要由協調者一件件補。

## 七、兩件要使用者定的

1. **模型**：九道的 `configured_model` 都是 `claude-opus-5`，但
   `session_context.model`、`last_served_model`、`user_switched_model` **全是
   `claude-sonnet-5`**——像是帳號層的切換，不是 trigger 設的，協調者改不動。

   （F 594→404 並留下可覆核的 verdicts.tsv）。**v2 開道前請先確認這個設定。**
2. **規模與花費**：v1 九道十一小時 471 美元。v2 五道、活少一半、第一段以規則為主，
   預估低於此，但仍是數百美元量級。

## 附：三個「都不報錯，都朝著看起來沒事的方向失效」的坑（lane-E 歸納）

v2 開跑一日之內，同一族的病現了三次。lane-E 把它們並在一起看：

| 病 | 徵候 |
|---|---|
| `pushmain.sh` 之 `--ours` 靜默刪行（坑 68、70） | 驗收全過、`verify` 全 0、推送成功，**唯獨資料少了** |
| 水位線之閘 `except` 靜默放行（坑 72） | 印一行字然後放行，而那行字混在七行正常輸出裡，`grep -q OK` 看不見 |
| 單分支 clone 靜默不更新分支 ref | `git fetch origin` 只更新 `origin/main`，跨分支比對讀到的是上次抓的快照 |

lane-E 的一句話值得抄在最前面：

> **查一個數對不對，得先問「我讀的這個數是什麼時候的」。**

### 各道之工作區是 `--depth 1` 的 clone，隱含 `--single-branch`

`remote.origin.fetch` 只有 `+refs/heads/main:refs/remotes/origin/main` 一條，
故 `git fetch origin` **永遠不更新 `origin/claude/qa2-*`**。兩個後果：
跨分支之賬比對讀到過期分支；stop-hook 拿 HEAD 比 `origin/<自己的分支>` 而報假的「有 N 筆未推」。

**凡要跑跨分支比對者，先補這一條再跑**：

```bash
git config --add remote.origin.fetch '+refs/heads/claude/qa2-*:refs/remotes/origin/claude/qa2-*'
git fetch origin
```

（水位線之閘不受此影響——它比的是本地賬與 `origin/main`，而 `origin/main` 正是單分支 clone
唯一會更新的那條 ref。）

### 提交訊息裡的反引號會被 shell 吃掉（lane-B 所報）

`git commit -m "…`backrefs.py --zombies`…"` —— 雙引號裡的反引號是**命令替換**，
shell 先去執行它、得 `command not found`、replace 成空字串，再把空字串交給 git。
**git 不報錯、提交成功、推送成功、`verify` 全綠，只有字沒了。**

而我們的提交訊息是 markdown，標記檔名／id／欄位名的正規寫法正是反引號
——**這個坑正對著我們的寫作習慣：愈是把訊息寫得規矩，愈容易踩。**

**一律用** `git commit -m "$(cat <<'EOF' … EOF)"`（**界詞必加單引號**）**或** `git commit -F <檔>`。
`pushmain.sh` 已加一道極輕之警（反引號數為奇即疑），不中止。
