# 补交：`collate-kaozhen`／`paddle-ocr-structured` 与云端道对不上的地方 ＋ 耗时数据

按 §八裁决要求补的两件事，写在这里（本道其余进展见另立的 status/done 单）。

## 一、两个 skill 与云端道对不上的地方（供协调者优化 skill）

1. **`paddle-ocr-structured` 整套走不了**：需要本地 GPU（PaddleOCR + CUDA），
   云端道没有 GPU、没有 `scripts/paddle-ocr/setup_env.sh` 依赖的本地 Python venv
   环境，`py -0` 那一步在云端环境无意义。**云端道只能走该 skill 文档里说的
   「不适用」分支之外的路子——视觉识别（`Read` 读 PNG）**，等于该 skill 对云端道
   唯一有用的部分是「版面分类规则」「四个坑」两节的**思路**（怎么判标目/正文/脚注/
   卷题），不是脚本本身。
2. **`paddle-ocr-structured` 的坑本身仍然有效，只是换了实现方式**：本卷视觉识别时
   确实遇到该 skill §「版面重建的四个坑」类似的问题（如姚振宗按语常年缀在引文段末、
   与引文同字号顺排，等价于坑一"取正文基线思路失效"——视觉识别下的应对是**认「按」
   字起头而非认坐标**，思路互通，值得在 skill 里加一句"若走视觉识别而非 PaddleOCR，
   坐标坑换成文字标记坑，判读逻辑仍适用"）。
3. **`collate-kaozhen` 的 CLI 部分（`python -m book_index_manager`）对本道无意义**：
   `--root` 指向 `D:/workspace` 这种本地路径假设是本机开发环境，云端道的工作区路径
   完全不同（`/home/user/...`），**这条不是 bug，是本道任务范围本就不包括入库**，
   但如果协调者要给下一批"入库道"派云端会话，需要在任务书里先把 `--root` 换算成
   云端路径讲清楚，否则会卡在第一步。
4. **`collate-kaozhen` 的"双文件原则"要求写入 `book-text` 仓**：本道工作区完全没有
   clone 这个仓（任务书没要求，铁律也不许碰 book-index/book-index-draft），所以
   **本道产出的 JSON 结构示例只能算「格式草稿」，物理上放不进正式路径**——这是任务书
   分工本身决定的（不入库=不写数据仓），不是本道疏漏，供协调者派下一道时确认对方
   会 clone `book-text`。

## 二、耗时数据（供估工量）

- `vol03.pdf` 下载完成：20:35:33（72 MB，几秒内完成，网络不是瓶颈）。
- 从下载完成到卷四（兵書略，34 页，56 条目）结构化清单与报告写完：**约 27 分钟
  墙钟时间**（20:35 → 21:02），这段时间内含：
  - 第一批（前期版面判定，约 15 页渲染阅读＋判断）
  - 第二批（卷四全部 34 页正文，含因跳页记录页码一度错位而**回读复核约 10 页**，
    实际 Read 调用约 45 次）
  - 期间的库内比对（grep/python 查 book-index 数据）与报告撰写
- **折算：视觉识别单页（含配套的实体识别、按语提炼、页码记录）约 20–30 秒**，
  这是"读一页 PNG＋当场判断内容归属"的综合耗时，不是纯 OCR 耗时——**纯识别本身更快，
  大部分时间花在"这条要不要单独列、按语从哪到哪"的结构判断上**。
- 据此估算：全书 466 页、约 5 倍于卷四的剩余篇幅（其余五卷合计约 410 book 页），
  若保持同一节奏，**纯阅读＋结构化预计还需 3–4 小时墙钟时间**（不含最终 JSON 转正式
  格式的逐字誊录，那部分本道未做，需要另估）。
