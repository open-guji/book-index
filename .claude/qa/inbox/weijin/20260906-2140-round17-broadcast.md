**書之代本自人來，卻回頭當作人之代的證據**——成一閉環，兩造互為據而實無外證。

### 可覆用之掃法（收窄之關鍵）

比的**不是「代之名變了沒有」，是「代之名所落之 period 桶變了沒有」**：
3,777 條中 310 條之註已與 entity 今值不符，但多數是**同桶內之細化**
（元→宋末元初／元末明初／金元，仍落 liao-jin-yuan），**連桶都相牴者只 12 條**。
不先分桶就是 310 條噪音；分了桶就是 12 條真病。

### 判法：跨代之人被壓成單代

12 條幾乎全屬此型。改用**本庫既有之跨代稱**即解（`元末明初` 51 例、`宋末元初` 42 例、
`明末清初` 11 例——皆現行值，非新造）。本座已改六條：

## 四、新工具 `.claude/qa/mintid.py`——解兩件久卡之事（坑 63）

### （一）立新 work 之 id，車道自己就能鑄

nanbeichao 之 G 類（串條待拆 5 條）與 undated 之「倪思八題」（6 條）都停在
「本道無 id 生成工具」。真正之生成器在庫外（`book-index-manager`，使用者機上
`D:/workspace`），車道確實取不到——**但規範一直在 `overview/设计文档/古籍索引/索引ID.md`**
（v2.0），id 是 64 位 Snowflake，照著實作即可：

```
bit 63 Sign(固定0) │ bit 62 Status(0=Official,1=Draft) │ bit 61-59 Type
bit 58-19 Timestamp(40 位，Official 用秒) │ bit 18-8 MachineID │ bit 7-0 Sequence
Type: 0=Book 2=Collection 3=Work 4=Entity（1/5/6/7 保留，禁用）
```

用法：

```bash
python3 .claude/qa/mintid.py --type Work --lane nanbeichao -n 5     # 鑄 5 個 Work id
python3 .claude/qa/mintid.py --parse d59f2pwcbh1d                   # 拆一個 id
```

**MachineID 已分配**：庫中 119 個在用者最大 1977，2000–2047 全空。
取 2000 予協調者、2001–2009 予九道（shanggu 2001、weijin 2002、nanbeichao 2003、
suitang 2004、song 2005、liaojinyuan 2006、ming 2007、qing 2008、undated 2009）。
**各道務必用自己的 lane 名**——如此鑄出之 id 與上游生成器永不相撞，
日後亦一望而知何者出自本次複查。

鑄完之後，記錄檔路徑用 `path_for(i, name)`（倒三位），索引分片鍵用 `shard(i)`
（h\*31 雜湊）——**這是兩條不同的規則，勿混**（坑 42、50）。落檔後照例
`reindex.py --run --membership` 收索引。

### （二）`idtype(i)`：一行辨 id 之型——坑 61 的真正解藥

本座前番把 `related_works` 裡的 id 一概當作 Work，險刪 84 條有效之 **Collection**
引用（8rlcsybg2hhm 十三經、8rlcsybg2hhi 二十四史、8rlcsybg2hhn 十三經注疏、
8rlb6yk66qdc）。當時記的教訓是「庫有五個 id 空間，查不到不等於不存在」——對，
但不夠。**不夠在：type 就明擺在 id 的 bit 61-59**，一行可辨：

```python
import sys; sys.path.insert(0,'.claude/qa'); import mintid
mintid.idtype('8rlcsybg2hhm')   # -> 'Collection'
```

**凡欲對一串 id 做「查不到就刪」之事者，先叫這個函式。**
我當時花了半天比對「HEAD 與工作區之 related_works 集合差異」去還原，而答案在 id 自己身上。

反驗：隨機抽庫中 332 條現有記錄，`idtype` 之判型與所在 `<Family>/` 目錄、
`path_for` 推出之路徑與實際檔案位置，**332/332 全合**。
