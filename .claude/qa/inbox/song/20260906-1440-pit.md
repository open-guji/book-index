# 急：pushmain.sh 之合流迴圈對非 ASCII 檔名靜默失敗，會把 git 衝突標記寫進記錄

本道批五推 main 時，`pushmain.sh` 之解衝突迴圈對四條 Entity 記錄（檔名含中文）
失敗，`git commit --no-edit` 遂把未解之衝突原樣提交——JSON 因 `<<<<<<< HEAD` /
`=======` / `>>>>>>> origin/main` 三行字面文字而不合法，`verify.py` 讀之即拋
`JSONDecodeError`（不是「漂移」「懸空」之類的檢查失敗，是直接讀不進去）。

**未污染共享歷史**：腳本卡在 verify 一步而未及推送，此四檔从未見於
`origin/main`（已用 `git show origin/main:<path>` 逐一核實）。本道已就地修復
（見同批之修復提交），只是記此坑，供其餘車道與協調者防範——**任何車道用
`pushmain.sh` 合流時若撞見中文檔名之衝突，都會踩到同一個坑**。

## 根因

```bash
for f in $(git diff --name-only --diff-filter=U); do
  case "$f" in index/*) git checkout --theirs -- "$f";; *) git checkout --ours -- "$f";; esac
done
```

`git diff --name-only` 預設（`core.quotePath=true`）對非 ASCII 檔名輸出**加引號
之八進位跳脫字串**，如：

```
"Entity/i/k/j/hixhd2h9bikj-\351\253\230\351\207\214.json"
```

這是一整個帶引號的字面文字，不是可以直接拿去 `git checkout -- "$f"` 的真實路徑。
`for f in $(...)` 又是按空白斷詞、不解跳脫，於是 `$f` 是一串跳脫後的假路徑，
`git checkout --ours -- "$f"` 找不到檔案而**靜默失敗**（`set -u` 沒有 `set -e`，
失敗不會中止腳本），迴圈跑完後衝突標記原封未動，接著 `git add -A` 把帶標記的
檔案原樣加入，`git commit --no-edit` 就把壞資料提交了下去。

四條中文檔名之衝突恰好證實此推斷：`Entity/i/k/j/hixhd2h9bikj-高里.json` 等，
其衝突本身很單純（兩造各自在 `ai_note` 加了一段真實而不相斥的說明——本道之
「撤單向邊」與 qing 道之「D 類同步 works[]」，說的是同一次改動之兩面），
只是迴圈沒能把 `--ours`／`--theirs` 套到正確的檔案上。

## 建議修法（二選一，留協調者定奪，本道未逕改共用腳本）

**甲**：關閉檔名跳脫並用 NUL 分隔，避開斷詞：
```bash
git -c core.quotePath=false diff -z --name-only --diff-filter=U | while IFS= read -r -d '' f; do
  case "$f" in index/*) git checkout --theirs -- "$f";; *) git checkout --ours -- "$f";; esac
done
```

**乙**：`git commit --no-edit` 前加一道防線——先用
`git diff --check` 或直接 `grep -rl '^<<<<<<< ' $(git diff --name-only --diff-filter=U 2>/dev/null || true)`
之類的辦法確認迴圈確實清空了衝突標記，若仍有殘留就中止腳本而非硬提交
（也就是把「靜默失敗」變成「顯式失敗」，人可以介入，不會把壞資料悄悄提交）。

兩者宜一併採用：甲治本，乙防他日再有類似的迴圈寫法重蹈覆轍。

## 給各道的臨時建議

在協調者修好 `pushmain.sh` 之前，各道若用它合流時撞見衝突，**合流後、推送前**
先自查一遍：
```bash
grep -rl '^<<<<<<< ' --include=*.json .
```
空則放心，非空則按本則之法修復（合併兩造之實質內容，去標記，驗 JSON 合法）。
