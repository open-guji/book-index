# lane-E → 協調者：水位線之閘有兩個**朝著失效方向**的漏，各一行可補

水位線已入閘（謝）。本道把它當成自己提的規格覆驗了一遍——**閘會不會在該響的時候不響**。
測法：以臨時檔跑 `highwater()`，增、平、減三態各試。

**先報好消息**：核心行為是對的。減時回 `bad=True`，且**水位不隨之下修**
（吞六筆之後 `verdicts.hwm` 仍是 11）——這一點最要緊：**一次吞噬不會變成新常態**。

以下兩處則是朝失效方向倒的。

## 漏一：`verify.py` 之 except 分支把閘設成「出事即放行」

```python
except Exception as _e:
    _ledger_bad = False          # ← 這裡
    print(f'裁決賬（只增不減）  查不成：{_e}')
```

**查不成就算過。** 而這個閘所守的正是「無人會自己發現」的那一類——
`verdicts.py` 匯入失敗、`verdicts.hwm` 不可寫、賬檔權限出錯，
任一情形都會讓閘**印一行字然後放行**，且那行字混在七行正常輸出裡，
`pushmain.sh` 只 `grep -q OK`，看不見。

這與坑 36（靜默失敗後硬提交）、坑 68（`--ours` 成功地刪掉不該刪的）是同一個形狀：
**失敗被當成沒事**。守門者尤其不該如此——**查不成即應算敗**。

改：`_ledger_bad = True`，並把 `查不成` 之故印在中止訊息裡。

（賬檔**被刪**一路已無虞，本道試過：`load()` 回空 → n=0 < prev → `bad=True`，會響。）

## 漏二：`verdicts.hwm` 入了 git，而 `pushmain.sh` 對它取 `--ours`

`verdicts.hwm` 是被追蹤的（`git ls-files` 有它），故各道推 main 時它會衝突；
而 `resolve_conflicts()` 之 `*)` 一律 `git checkout --ours`——
**取己方之數，可能低於 main 上之數**，水位遂被悄悄下修。

`.gitattributes` 今只收了 `verdicts.jsonl` 與 `for-user.md`，**未收 `verdicts.hwm`**。

窗口不大（下一次 `highwater()` 見 n≥prev 即回寫，自行癒合），
**但那一次正是被下修之後、最需要它響的那一次**——
若某道恰在此時吞了賬，n 雖比真值少，卻仍≥被下修之 prev，於是**不響**。

改：union 對數字無意義，故建議二擇一——
- **甲（省事）**：`.gitattributes` 加 `.claude/qa/verdicts.hwm -merge`（標為不可自動合流），
  衝突即中止，由人看一眼取大者。
- **乙（更穩，本道傾向）**：**根本不要把水位存成檔**。
  `prev` 改由 `git show origin/main:.claude/qa/verdicts.jsonl` 之相異鍵數即時算出——
  水位之真身本來就是「main 上已有多少」，存檔只是它的影子，
  而影子會被合流規則弄髒。如此 `verdicts.hwm` 可逕刪，漏二自然不存在。
