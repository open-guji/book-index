## 三、五件容易漏的——本道怎么办的

1. **draft 侧索引怎么处置**：查证结果——本批迁移/标记的字段（`alt_names`／
   `external_ids.*`／`_promoted_to`／`_promoted_at`／`merge_history`／`merged_from`）
   **没有一个在 `.claude/qa/reindex.py` 的 `expect_ent()`／`verify.py` 的漂移检查
   范围内**（那五个受检字段是 `primary_name`／`dynasty`／`birth_year`／`death_year`／
   `period`，本批一个都没碰）。**结论：本批不需要跑任何 reindex**，两侧
   `index/entities/*.json` 原封不动即为正确状态。
   （教训：曾误跑 `book-index reindex --target official/draft`——那是
   book_index_manager 的全量深度重建 CLI，会把 Work/Book/Collection 的索引也
   一并按它自己的（与本仓 `verify.py` 不一致的）算法重写，凭空造出 188 条
   Work `dynasty` 漂移。已用 `git checkout -- index/` 撤销，改用"先查字段是否
   在受检范围内"这一步来判断根本不需要 reindex，而不是无脑跑全量重建。
   这条踩坑写进 `进度/G-工具分发与网站/` 供他道参考更稳妥，本道先记在此。）
2. **A2 `alt_names` 去重判据**：按 `name` 精确字符串去重（`production 已有的
   name 集合` 之外的才追加）。**不做"一字之差"的模糊/异体判断**——查了一个实例
   （周金：production 原有「約庵」，draft 有「約菴」，两者是常见异体但不在
   `scan.py` 的 `VARIANTS` 表内），若按"看着像"去重会把两个不同写法当同一个
   丢掉一个，而项目明训"不是一字之差就算，是逐对裁定的字表"（坑 15）。
   故迁移后这条记录 alt_names 里"約庵"「約菴」两个都在，**这不是 bug，是遵守
   既有纪律的结果**——若日后判定这两个确系同一别名的异体，那是 qa_entity.py
   的 `NAM02` 或人工核查该做的事，不该在併條这一步顺手模糊处理。
   "同名不同 type"的情形本批**没有出现**（A2 清单里的"增量 name"定义就是
   production 侧完全没有的 name，不会撞上已有 name 的不同 type）。
3. **`merge_history.reason` 写法**：`"draft/production 同人同书重出（CBDB
   auto_create 批次遗留），2026-09-09 併條"`，照任务书建议原样写。
