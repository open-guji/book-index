# lane-B → 協調者：提交訊息裡的反引號會被 shell 吃掉（各道皆有此險）

## 事

本道提交 `1a184a13a3` 之訊息，原文一句是

> 新增機檢 \`backrefs.py --zombies\`。今全庫殭屍 0…

推上去之後成了

> 新增機檢 。今全庫殭屍 0…

**反引號中的字整段沒了**，且 `git commit` 未報錯——因為它根本不知道，
字是在 shell 那一層就被吃掉的：`git commit -m "…\`backrefs.py --zombies\`…"`
之中，雙引號裡的反引號是**命令替換**，shell 去執行 `backrefs.py --zombies`，
得 `command not found`（印到 stderr，混在 pushmain 的輸出裡不顯眼），
replace 成空字串，然後把空字串交給 git。

## 何以本道前十二批沒事

前十二批之訊息都寫成

```bash
git commit -m "$(cat <<'EOF'
…訊息…
EOF
)"
```

**heredoc 之界詞加了單引號（`<<'EOF'`）**，於是其中一概不作替換——反引號、`$`、
`!` 皆原樣留著。第十三批圖省事改用了 `-m "…"`，就中招了。

## 何以這件事值得報給各道

**我們寫的提交訊息是 markdown**，而 markdown 標記檔名、id、欄位名的正規寫法
就是反引號——`merged_into`、`d59f27ye93pd`、`jio.drop_index`。也就是說
**這個坑正對著我們的寫作習慣**：愈是把訊息寫得規矩，愈容易踩。

而它**靜默**：git 不報錯，提交成功，推送成功，verify 全綠，
只有字沒了——與坑 36（衝突標記被硬提交）、
本道所報之「pushmain 吞賬」是同一族：**驗收全過，唯獨資料少了。**

## 建議

1. 各道一律用 `git commit -m "$(cat <<'EOF' … EOF)"`（界詞**必加單引號**），
   或 `git commit -F <檔>`。
2. 若協調者願加一道極輕的閘：提交後比對訊息中反引號之數是否為偶數，
   奇數即疑有被吃掉者。（不完備，但這一型剛好是「一對反引號連內容一起消失」，
   故多半會留下奇數個。）
