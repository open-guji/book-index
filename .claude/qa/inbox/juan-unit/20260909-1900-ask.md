juan_unit 调研：三处与任务书/任务档实测对不上，以实测为准

## 一、"影响 3 万多条没有 measure_info 的条目"——量级估计偏差较大

任务档原话："改成留空还是保留「卷」为默认，影响 3 万多条没有 `measure_info` 的
条目怎么显示"。

**实测**：无 `measure_info` 的确有 29,093 条，但拆开看：

| | 条数 |
|---|---:|
| 无 `measure_info`，`juan_count.number>0`（真正需要单位决策） | 38 |
| 无 `measure_info`，`juan_count.number=0`（"不分卷"类，早不需要单位） | 312 |
| 无 `measure_info`，`juan_count` 本来就无值（不受默认值影响） | 28,743 |

**受"默认值改不改"这个决策实际影响的条目量级，加上 noop 桶里同类情形与真无从判，
一共约 145 条，不是 3 万多条**。3 万多条那个数没错（是"无 measure_info"的真实
总数），但它和"受默认值渲染规则影响的条目数"不是一回事——99% 的"无 measure_info"
记录本身也没有真实 `juan_count`，不会因为默认值变了而多显示或少显示任何东西。
这处出入不影响任务档「甲案」本身，但会影响协调者判断这件事的优先级/风险面，
故列出。详见全量报告表五。

## 二、任务档举的"春秋"无从判例，本次全量扫描未能精确复现

任务档原文举例："`春秋`＝「古經十二篇（依十二公）／今文經十一卷」——两种传本
各自的量不同"。

**实测**：全库扫描找到的"多量词并存且不含卷"（真正对应这个陷阱类型的）只有
16 条，逐条核对题名与 `measure_info` 原文，**没有一条是"春秋"，也没有一条是
"古經…篇／今文經…卷"这个具体句式**。这 16 条清一色是通俗小说的"集/編/函＋回/種"
结构（如"洪秀全演義＝二集二十九回"），性质上更接近"套书按集/编/函分册、每册
再计回/種"，而非"两种传本各记各的量"。

不确定原因：可能是任务档举例时用的是转述/简化后的示意句，不是库中某条记录的
逐字原文；也可能"春秋"相关的那条记录标题/measure_info 与我搜到的不完全一致
（本库有多条以"春秋"起首或含"春秋"的记录，但均无"篇"与"卷"并存的写法）。
**没有据此改判据**——"版本互异"这一类在概念上仍然成立（本项目对经典的多传本
处理本来就常见），只是本次全量扫描里没能找到任务档举的那个具体例子对应的记录，
如实报告，供协调者核实原始出处或更正举例。

## 三、自己撞见的第五个陷阱（任务档四个陷阱之外）：CJK 兼容字

不算"实测对不上任务档"，是任务档没提过的新坑，记在这里方便协调者决定要不要
补进 PITFALLS.md 或任务档的陷阱清单：

`西泠閨詠` 的 `measure_info` 原文"十六卷"里，"六"字实际 Unicode 码位是
`U+F9D1`（CJK Compatibility Ideograph，canonical decomposition 到标准的
`U+516D`），肉眼、`repr()` 都看不出差别。任何未做 `unicodedata.normalize
('NFKC', s)` 就直接用字符类做正则的量词抽取脚本，会把"十六"拦腰截成"十"＋
孤立的"六"，量词判断静默漏判。已在归一化后重新统计，全库这类问题目前只影响
极小一部分记录（本次未穷举具体条数，不在本批范围），但**建议往后任何量词/数字
抽取脚本都先 NFKC 归一化**，这条已写进 `scan_juan_unit.py` 与全量报告。
